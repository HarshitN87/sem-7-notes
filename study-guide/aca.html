Part I — Unit One

Basics of Computing, Technology Trends & Performance Laws

"Before one can run a Grand Hotel at breathtaking speed, one must understand the blueprints, the electricity bill, the cost of broken porcelain, and why speeding up only the elevator will never fix a slow concierge."

1.1 What is Computer Architecture? (And How It Differs from Organization)

If you feel intimidated by the words Advanced Computer Architecture, take a deep breath. Strip away the jargon and look at the word Architecture in ordinary life. When an architect designs a hotel, they do not personally lay every brick or twist every copper wire. Instead, they decide how the building is experienced by the people who use it: how many floors exist, where the grand staircase sits, how guests check in, and what doors connect to what hallways.

In Computer Science, Computer Architecture is the exact same idea: it is the art and science of coordinating many levels of abstraction—from silicon atoms all the way up to your Python or C++ code—to build a machine that is faster, cheaper, more reliable, and less power-hungry. Technically, computer architecture consists of three tightly coordinated pillars:

  • Instruction Set Architecture (ISA): The contract between hardware and software. It specifies what instructions the CPU understands, what registers exist, how memory is addressed, and what data types are supported.
  • Microarchitecture (Computer Organization): The actual internal plumbing—pipelines, caches, ALUs, branch predictors, and control circuits—that makes the ISA work in silicon.
  • System Design: Everything else that turns a bare processor chip into a living computer: memory controllers, buses, multiprocessor interconnects, Direct Memory Access (DMA), and I/O devices.
Analogy Corner — The Piano & The Pianist

Think of a piano's 88 black-and-white keys as the Computer Architecture (ISA). Any pianist in the world can sit down and play Mozart because the interface (the keys) is standardized. Now open the lid of the piano: whether the sound is produced by wooden hammers striking steel strings (a grand piano) or by digital microchips and speakers (a Yamaha keyboard) is the Computer Organization (Microarchitecture). Same architecture, wildly different organization!

The Stack of Abstraction & The Five Forces

Modern computing survives only because of levels of abstraction. Going from top to bottom: Application → Operating System → Compiler & Firmware → Instruction Set Architecture (ISA) → Instruction Set Processor & I/O → Datapath & Control → Digital Logic Gates → Transistors & Circuits → Silicon Layout. Every layer hides the messy details of the layer below it.

Meanwhile, computer architects are constantly pulled in five directions by five powerful forces: Technology (what silicon can physically do this year), Applications (AI, 3D movies like Shrek, weather forecasting, web servers), Programming Languages, Operating Systems, and History (also called backward compatibility—the heavy inertia of old software that customers refuse to throw away, summarized playfully in the lecture notes by Newton's law A = F / M, where big legacy mass M slows down architectural acceleration A!).

Historical Interlude — From Room-Sized Giants to Pocket Supercomputers

Pre-WWII: Mechanical calculating machines with gears. 1940s–1950s: Relays gave way to glowing vacuum tubes (like ENIAC, which weighed 30 tons), and the first high-level languages (FORTRAN) were born. 1960s: Transistors and Integrated Circuits (ICs) shrank computers from rooms into mainframes overseen by white-coated operators. 1970s: The "Semantic Gap" era—architects tried to put complex high-level language features directly into hardware via microcoding (giving rise to CISC). Minicomputers introduced time-sharing. 1980s: The "Keep It Simple, Stupid" (KISS) revolution gave birth to RISC, shifting complexity from hardware to smart compilers. 1990s–Present: With millions and then billions of transistors per chip, architects asked, "What do we do with all these transistors?" The answer: huge on-chip caches, branch predictors, out-of-order speculative execution, and multi-core processors.

1.2 Instruction Set Architecture (ISA) & RISC vs CISC

PYQ Spotlight — Dec 2023 Q1(b)

Question: Delve into the concept of Instruction Set Architecture (ISA), its role in bridging the gap between hardware and software, and the significance of a well-defined ISA in computer system design.

The Instruction Set Architecture (ISA) is the single most important boundary line in all of computer engineering. Imagine two teams who never want to learn each other's jobs: Software Engineers / Compiler Writers (who turn C, Java, or Python into machine instructions) and Hardware Engineers (who arrange billions of transistors). The ISA is the legal treaty between them.

Because of the ISA, a software programmer does not need to know how many pipeline stages an Intel Core i9 has, and a hardware designer does not need to know how Microsoft Excel is coded. Both simply obey the ISA. Specifically, an ISA defines all programmer-visible components:

  • Instruction Set & Opcodes: The exact vocabulary of operations (ADD, SUB, LOAD, STORE, BEQ) and their binary encoding (instruction format: e.g., 4-bit opcode + operand references).
  • Register Set: How many fast internal storage slots exist, how wide they are (32-bit or 64-bit), and how they are used.
  • Memory Organization & Addressability: How big the address space is, whether memory is byte-addressable, and byte ordering (Big-Endian vs Little-Endian).
  • Data Types & Addressing Modes: Supported formats (bytes, words, integers, floats) and the rules for finding operands in registers or memory.

What makes a GREAT ISA? Three golden qualities: (1) Implementability—it can be built cheaply for budget chips AND super-fast for flagship chips; (2) Programmability—compilers can easily translate high-level code into it; and (3) Backward/Forward Compatibility—a program compiled in 1995 still runs on a 2026 chip (e.g., the legendary x86 family from Intel 8086 in 1978 through 286, 386, 486, Pentium, and modern x86-64). Other famous ISAs include ARM (Acorn RISC Machine—dominating smartphones and Apple Silicon), MIPS (Microprocessor without Interlocked Pipeline Stages—the darling of university textbooks), SPARC (Sun Microsystems), PIC, and Z80, plus SIMD extensions like Intel MMX, SSE, AVX and AMD 3DNow!.

RISC vs CISC — Two Philosophies of ISA Design

In the 1980s, computer architecture split into two warring philosophies. CISC (Complex Instruction Set Computer)—championed by x86 and VAX—believed a single powerful instruction should do a whole job (like loading from memory, multiplying, and storing back) to save code size. RISC (Reduced Instruction Set Computer)—pioneered by David Patterson (Berkeley) and John Hennessy (Stanford)—argued that simple, uniform instructions execute in a single clock cycle and glide smoothly through a pipeline.

1.3 Classes of Computers & The Myopic View of Computer Architecture

Not every computer wants the same thing. A computer inside your microwave has completely different goals from a server running Amazon. Today, computing divides into three major classes:

  • Desktop / Personal Computers ($500–$5K system, $50–$500 CPU): General-purpose workhorses (e.g., Intel Core, AMD Ryzen/Opteron). Goals: best price-performance ratio and graphics performance.
  • Servers ($5K–$5M system, $200–$10K CPU): Backbone of the web, databases, and cloud (e.g., Intel Xeon, IBM Power, Sun Niagara). Goals: massive throughput (transactions/sec), availability/reliability (never go down!), and scalability. Cost is secondary.
  • Embedded Computers ($10–$100K, CPU as cheap as $0.01–$100): Hidden inside smartphones, cars, pacemakers, routers, and washing machines (e.g., ARM, MIPS, XScale). Goals: ultra-low cost, tiny power consumption, small physical size, and real-time deadlines.
PYQ Spotlight — Dec 2022 Q1(a)

Question: Discuss the Myopic View of Computer Architecture.

In medicine, myopia means nearsightedness—you can only see what is right in front of your nose and blur out the bigger picture. In our syllabus, the Myopic View of Computer Architecture is a famous warning against designing a computer by staring only at the CPU's raw clock speed or ISA while ignoring the rest of the system!

Historically, engineers suffered from this tunnel vision: they obsessed over making the CPU core faster (higher GHz, fancier instructions) and treated memory, I/O, compilers, operating systems, power budgets, heat dissipation, and cost as "someone else's problem." Why is this myopic view disastrous?

  1. The Memory Wall: A 5 GHz CPU is completely useless if it spends 90% of its life sitting idle waiting for slow DRAM to deliver data.
  2. The Power Wall: Doubling clock frequency without watching power melts the chip and drains batteries.
  3. Software & Compiler Blindness: A brilliant hardware feature that compilers cannot easily use (or that breaks OS virtualization) adds cost for zero real-world speedup.
  4. Holistic Truth: Real computer architecture is a system-wide balancing act among performance, energy, cost, dependability, memory hierarchy, and software ecosystem.

1.4 Moore's Law & Trends in Technology, Power, Cost, and Dependability

PYQ Spotlight — Dec 2022 Q1(c) & Dec 2023 Q1(c)

Question: State and briefly describe Moore's Law.

Historical Interlude — Gordon Moore's 1965 Prediction

On April 19, 1965, Gordon E. Moore (who later co-founded Intel) published a short article in Electronics Magazine noticing that the number of transistors engineers could squeeze onto an affordable integrated circuit was doubling roughly every year—later refined in 1975 to every 18 to 24 months. It is not a law of physics like gravity; it is an empirical rule of thumb and self-fulfilling industry roadmap that drove the greatest technological explosion in human history.

Moore's Law states that the number of transistors on an affordable microchip doubles approximately every 18 to 24 months, which historically led to exponential increases in computing power and exponential drops in cost. A chip with 2,000 transistors that cost $1,000 in 1970 cost less than $0.02 to manufacture decades later!

Pn = P0 × 2n Where P0 = initial transistor count/power, Pn = future count, and n = (number of years) / 2 (assuming doubling every 2 years).
Example (from notes): Intel 386 SX in 1988 had 275,000 transistors. In 1997 (9 years later, n = 4.5): Pn = 275,000 × 24.5 ≈ 6.2 million transistors!

The Slowdown / Collapse of Moore's Law: Even Gordon Moore admitted, "It can't continue forever." As transistors shrink down to a few nanometers (the width of a handful of silicon atoms), electrons start leaking through barriers via quantum tunneling, and heat becomes impossible to remove. Physicists like Michio Kaku note that traditional 2D silicon scaling is reaching atomic limits, pushing the industry toward 3D stacked chips, multi-core architectures, specialized AI accelerators, molecular computing, and quantum computers.

Bandwidth vs. Latency & Wire Scaling

Two numbers rule technology trends: Bandwidth (Throughput)—total work done per unit time (like how many lanes a highway has)—and Latency (Response Time)—how long a single trip takes from start to finish. Over decades, processors saw 10,000–25,000× bandwidth gains, while latency improved only 30–80× (and for memory/disks, latency improved only 6–8×!). A famous rule of thumb: Bandwidth grows roughly as the square of latency improvement. Meanwhile, wire delays do not scale well: as wires get thinner, their resistance (R) and capacitance (C) per unit length increase, so signal propagation delay ($R \times C$) eats up an ever-larger slice of the clock cycle.

Power & Energy Trends (The Real Wall of Modern CPUs)

Beginners always confuse Power and Energy. Let's fix that forever:

  • Power (Watts = Joules/second): How fast you are burning electricity right now. Power determines your cooling fan size, heat sink, and power supply. Peak Power is the maximum surge (if exceeded, voltage droops and the CPU crashes). TDP (Thermal Design Power) is the sustained heat the cooling system must remove (lower than peak, higher than average).
  • Energy (Joules = Power × Time): The total fuel burned to finish a job. Energy determines your phone's battery life and a data center's electricity bill. Example: If Processor A uses 20% more power (1.2×) than Processor B, but finishes the task 30% faster (0.7× time), its relative energy is $1.2 \times 0.7 = 0.84$—Processor A is actually MORE energy efficient!

Total chip power has two components: Total Power = Dynamic Power + Static (Leakage) Power.

Powerdynamic = ½ × C × V2 × f   |   Energydynamic = C × V2   |   Powerstatic = Istatic × V C = Capacitive load, V = Supply Voltage, f = Switching Frequency. Notice V is SQUARED! Lowering voltage dramatically slashes both power AND energy, whereas lowering clock frequency f lowers power but NOT dynamic energy (since the task just takes proportionally longer!).
WORKED EXAMPLE (From Lecture Notes): A CPU runs in Mode-1 (1.0 V, 3 GHz) vs Mode-2 (0.75 V, 2 GHz). Find dynamic energy & power savings. 1. Energy Ratio = (V2)^2 / (V1)^2 = (0.75)^2 / (1.0)^2 = 0.5625 --> 43.75% (~44%) Energy Savings! 2. Power Ratio = [(0.75)^2 * 2] / [(1.0)^2 * 3] = 1.125 / 3 = 0.375 --> 62.5% Power Savings!

Trends in Cost & Fabrication Yield (WITH DEC 2022 PYQ SOLVED!)

Why does a huge GPU cost $1,500 while a tiny microcontroller costs $0.50? Three forces lower cost over time: Time (learning curve makes fabs more efficient), Volume (mass production), and Commodification (competition).

Chips are baked like microscopic cookies on circular silicon disks called Wafers, then sliced into individual rectangular chips called Dies. Because microscopic dust specks create random defects on the wafer, some dies are dead on arrival. The percentage of working dies is called the Die Yield. Crucially, Die Cost grows roughly as (Die Area)4—making a chip twice as big makes it much more than twice as expensive because fewer fit on a wafer AND each big die is much more likely to catch a dust defect!

Die Yield = Wafer Yield × ( 1 + (Defects per unit area × Die Area) / α )-α Standard textbook value (Hennessy & Patterson): α = 4 (manufacturing complexity parameter), Wafer Yield ≈ 1.0 (100%).
Also: Die Area ≈ (Wafer Area) / (Dies per Wafer) = (π × (d/2)2) / (Dies per Wafer), and Cost per Die = Cost of Wafer / (Dies per Wafer × Die Yield).

Dependability: Reliability & Availability

Cloud providers sign a Service Level Agreement (SLA) promising their servers will stay up. A system flips between two states: Service Accomplishment (working as promised) and Service Interruption (broken). Going from working to broken is a Failure; fixing it is Restoration.

  • MTTF (Mean Time To Failure): Average time a module works before breaking. Measures Reliability.
  • FIT (Failures In Time): $1 / \text{MTTF}$, traditionally reported as failures per billion hours of operation.
  • MTTR (Mean Time To Repair): Average time it takes to fix a broken module.
  • MTBF (Mean Time Between Failures): $\text{MTBF} = \text{MTTF} + \text{MTTR}$.
  • Module Availability: The fraction of time the system is actually working: $\text{Availability} = \frac{\text{MTTF}}{\text{MTTF} + \text{MTTR}}$. (e.g., "Five Nines" = 99.999% availability = only ~5 minutes of downtime per year!).

1.5 Classification of Parallel Computers (Flynn's Taxonomy & Grain Size)

PYQ Spotlight — Dec 2023 Q1(a) & Dec 2024 Q5(c)

Questions: (1) Elaborate on Flynn's taxonomy with real-world examples and modern applicability. (2) Explain classification of parallel computers based on (i) Grain Size and (ii) Instruction and Data Stream.

In 1966, Michael J. Flynn came up with the most famous classification scheme in all of computer architecture: Flynn's Taxonomy. He asked two brilliantly simple questions: How many independent streams of instructions are running at once? And how many independent streams of data are being processed at once? That gives a neat 2×2 grid:

Exhibit 1.1 — Flynn's Taxonomy (1966): The Four Kingdoms of Computing
  • SISD (Single Instruction, Single Data): One chef following one recipe on one bowl of batter. Classic von Neumann uniprocessor (e.g., old Intel 8086, Pentium 1). Today, mostly found inside tiny embedded microcontrollers.
  • SIMD (Single Instruction, Multiple Data): A drill sergeant shouts "Add 5!" and 1,000 soldiers simultaneously add 5 to their own numbers. One Control Unit broadcasts the same instruction to many Processing Units. Modern applicability: Huge! Powers NVIDIA/AMD GPUs, AI deep learning, video editing, photo filters (brightening millions of pixels at once), vector processors, and CPU extensions (Intel SSE/AVX, ARM NEON).
  • MISD (Multiple Instruction, Single Data): Multiple different algorithms run simultaneously on the exact same stream of data. Rarely used commercially, except in ultra-reliable fault-tolerant systems (like NASA's Space Shuttle flight computers, where 3+ independent computers check the same sensor data and vote!) and certain Systolic Arrays / near-memory automata.
  • MIMD (Multiple Instruction, Multiple Data): A bustling hotel kitchen where 8 chefs cook 8 completely different dishes using 8 different sets of ingredients at the same time. Modern applicability: The undisputed king of general-purpose computing—every modern smartphone, laptop (Intel Core i7, Apple M-series), server, and supercomputer cluster is MIMD.

Classification Based on Grain Size (Granularity)

Grain Size measures the ratio of computation time to communication time—basically, how big each chunk of parallel work is before processors need to talk to each other:

  • Fine-Grained Parallelism: Tiny tasks (a few instructions, < 20 instructions) with very frequent communication. High overhead, best handled directly in hardware (e.g., Instruction-Level Parallelism, SIMD, GPUs).
  • Medium-Grained Parallelism: Moderate tasks (hundreds to thousands of instructions, like parallel loops or threads inside one program). Balances communication overhead and load balancing well (e.g., OpenMP threads on multi-core CPUs).
  • Coarse-Grained Parallelism: Huge independent tasks (entire processes or programs running for millions of instructions with rare communication). Very low communication overhead, ideal for distributed clusters and cloud servers (e.g., MPI jobs, independent web requests).

1.6 Performance Metrics, Benchmarks, Iron Law, Amdahl's Law & Lhadma's Law

PYQ Spotlight — Dec 2022 Q1(b,c), Dec 2023 Q1(c), Dec 2024 Q1(b), Q3(b), Q4(c), Q5(a)

This single section is an absolute GOLDMINE for exams—almost every paper asks 10 to 20 marks from here!

1. Response Time vs. Throughput

Response Time (Execution Time / Latency) is how long it takes to finish one task from start to finish (what YOU care about when opening Photoshop). Throughput (Bandwidth) is the total number of tasks finished per unit time (what a Google data center manager cares about). Upgrading to a faster CPU improves both; adding more CPUs mainly improves throughput. And remember: $\text{Performance} = \frac{1}{\text{Execution Time}}$. If Computer A runs a program in 10s and Computer B takes 20s, A is $20/10 = 2\times$ faster than B.

2. The Iron Law of Processor Performance

The Iron Law of Performance is the master equation of CPU speed. It breaks total execution time into three crystal-clear factors:

Texec = Instruction Count (IC) × CPI × Clock Cycle Time (Tclock) Texec = ( IC × CPI ) / Clock Rate (f) IC = number of instructions executed (depends on Algorithm, Compiler, ISA).
CPI = average Cycles Per Instruction (depends on ISA & Microarchitecture; IPC = 1/CPI).
Tclock = seconds per clock tick (depends on Silicon Technology & Pipeline Depth).
PYQ SOLVED — Dec 2024 Q3(b)

Question: A processor has a clock rate of 2 GHz. It executes a program with 5 billion instructions, where the CPI is 1.5. Calculate the execution time.

Given: - Clock Rate (f) = 2 GHz = 2 × 10^9 cycles/second - Instruction Count (IC) = 5 billion = 5 × 10^9 instructions - CPI = 1.5 cycles/instruction Formula (Iron Law): T_exec = (IC × CPI) / Clock Rate = (5 × 10^9 × 1.5) / (2 × 10^9) = 7.5 / 2 = 3.75 seconds. ANSWER: The execution time is 3.75 seconds.

3. Benchmark Standards

How do you fairly compare an Intel CPU against an AMD CPU? You can't trust marketing claims! You run standardized test programs called Benchmarks. Real applications (Photoshop, Excel, compilers) are best, but when unavailable, engineers use three approximations:

  • Kernels: Small, compute-heavy core loops extracted from real programs (e.g., Livermore Loops, LINPACK).
  • Toy Programs: Tiny ~100-line textbook programs (e.g., Quicksort, Sieve of Eratosthenes, Puzzle). Easy to run, too simple to trust for big servers.
  • Synthetic Benchmarks: Artificially crafted programs designed to mimic average instruction mixes (e.g., Whetstone for floating-point, Dhrystone for integer).
  • Industry Standard Suites: Most famously SPEC (Standard Performance Evaluation Corporation)—such as SPEC CPU (Integer + Floating Point), SPECweb, SPECviewperf—along with TPC (Transaction Processing Council for databases) and EEMBC (for embedded systems).

4. Amdahl's Law (The Law of Diminishing Returns)

In 1967, IBM architect Gene Amdahl delivered a sobering mathematical truth: the performance improvement you get from speeding up one part of a system is strictly limited by the fraction of time that part is actually used.

Analogy Corner — The Delhi-to-Dehradun Trip

Suppose your trip takes 1 hour to get through airport security (serial, cannot be sped up) and 1 hour flying (parallelizable). Even if you invent an infinitely fast teleportation jet that reduces flight time to 0 seconds, your trip STILL takes 1 hour! Your maximum possible speedup is only 2×. That is Amdahl's Law in one breath.

Speedupoverall = 1 / [ (1 − f) + (f / S) ] Where f (or P) = fraction of execution time enhanced/parallelized (0 to 1), and S (or n) = speedup factor of the enhanced part (or number of processors).
Derivation: Told = 1 = (1−P) + P. With n processors, Tnew = (1−P) + P/n. Therefore Speedup = Told / Tnew = 1 / [(1−P) + P/n].
PYQ SOLVED — Dec 2024 Q1(b) & Q4(c)

Problem A (Dec 2024 Q1b): Using Amdahl's Law, determine the speedup for a program where 60% of the code is parallelized and 40% is sequential, with 4 processors.

Given: P = 0.60, (1 - P) = 0.40, n = 4 Speedup = 1 / [ 0.40 + (0.60 / 4) ] = 1 / [ 0.40 + 0.15 ] = 1 / 0.55 = 1.818x (approx. 1.82x speedup!)

Problem B (Dec 2024 Q4c): A new Web-serving processor is 10× faster on computation. The original processor spends 40% of time on computation and 60% waiting for I/O. What is the overall speedup?

Given: Fraction enhanced f = 0.40, Unenhanced (I/O) = 0.60, Enhancement Speedup S = 10 Speedup = 1 / [ (1 - 0.40) + (0.40 / 10) ] = 1 / [ 0.60 + 0.04 ] = 1 / 0.64 = 1.5625x (approx. 1.56x overall speedup!)

5. Lhadma's Law (Amdahl Spelled Backwards!)

PYQ Spotlight — Dec 2022 Q1(c) & Dec 2023 Q1(c)

Exam Trap Alert! Almost every student blanks out when they see "Lhadma's Law" on the exam paper. Look at the spelling: L-H-A-D-M-A is literally A-M-D-A-H-L spelled backwards!

Lhadma's Law is the witty, inverted twin of Amdahl's Law. Whereas Amdahl's Law tells you the golden rule of optimization—"Make the Common Case Fast"—Lhadma's Law warns you about the flip side: "While making the common case fast, do NOT make the uncommon case catastrophically slow!"

Why? Because if an "uncommon" event that used to take 1% of execution time gets slowed down by 100× (because you stripped away its hardware support to optimize the common case), that 1% suddenly balloons into 100% of your original runtime and destroys all your hard-earned gains! Lhadma's Law also highlights diminishing returns: once you optimize the easy common cases, the remaining unoptimized parts dominate execution time, so further effort yields near-zero speedup.

The Architecture of Memory: Caches, Coherence & Virtual Illusions

"A brilliant mind is wasted if it must walk three miles to the archive every time it needs a single telephone number. Hence, the Desk, the Bookshelf, the Library, and the Warehouse."

2.1 Why Do We Need a Memory Hierarchy? (The Grand Illusion)

Every programmer dreams of a magical computer with infinite memory that responds instantly and costs almost nothing. Unfortunately, physics laughs at that dream. Since the 1980s, processor speed skyrocketed exponentially while Main Memory (DRAM) speed crawled upward at a snail's pace—creating the famous Processor-Memory Performance Gap (the "Memory Wall").

Even worse, fast memory (like SRAM) takes 6 transistors per bit, making it physically huge, power-hungry, and wildly expensive. Cheap, spacious memory (like DRAM or Hard Disks) is painfully slow. A CPU register responds in 0.3 nanoseconds; a spinning magnetic disk takes 5 to 10 milliseconds—more than 10 million times slower!

How do computer architects solve this impossible triangle of Speed vs. Size vs. Cost? By building a Memory Hierarchy—a pyramid of progressively larger, slower, and cheaper memories stacked beneath the CPU.

Analogy Corner — The Scholar's Study

Imagine you are writing a research paper: 1. Your Hands / Sticky Notes (CPU Registers): Holds 3 facts, instant access (0.3 ns). 2. 2.2 Locality of Reference & Coherence Properties

PYQ Spotlight — Dec 2022 Q2(a), Dec 2023 Q2(a), Dec 2024 Q1(a)

Asked EVERY SINGLE YEAR! (1) Explain coherence and locality properties in detail. (2) Differentiate between Read Coherence and Write Coherence, when they are crucial, and mechanisms to maintain them.

A. Principle of Locality (Why Caches Actually Work!)

If programs jumped randomly around 16 GB of RAM, a tiny 64 KB cache would be useless. Thankfully, real programs are creatures of habit! The empirical 90/10 Rule observes that a program spends 90% of its execution time inside just 10% of its code (loops, frequently called functions, hot variables). This predictable habit is called the Principle of Locality, and it has two flavors:

  • Temporal Locality (Locality in Time): If the CPU accesses a memory item right now, it is very likely to access the exact same item again soon. Example: a loop counter i, a running total sum, or the instructions inside a for loop. How hardware exploits it: Keep recently used items in the cache!
  • Spatial Locality (Locality in Space): If the CPU accesses memory address X, it is very likely to access nearby addresses (X+1, X+2, X+3...) soon. Example: scanning through an array A[0], A[1], A[2], or executing sequential instructions. How hardware exploits it: Never fetch just 1 byte from RAM—fetch an entire contiguous block (cache line) of 16, 32, or 64 bytes at once!

B. Coherence Properties: Read Coherence vs. Write Coherence

Because the same piece of data gets copied into multiple places (Main Memory, L3 Cache, Core 0's L1 Cache, Core 1's L1 Cache), we need a strict guarantee called Coherence: any read of a memory location must always return the most recently written value to that location. Specifically, exams love asking the difference between Read Coherence and Write Coherence:

Feature Read Coherence Write Coherence
Core Definition Guarantees that whenever ANY processor reads a memory location X, it sees the most up-to-date value written to X, never a stale cached copy. Guarantees that writes to the same memory location X by multiple processors are serialized—every processor observes writes to X in the exact same order, and updates propagate cleanly without corrupting memory.
What Goes Wrong Without It? Core A updates balance = 500 in its L1 cache; Core B reads its own stale L1 cache and still sees balance = 1000! Core A writes X = 1 and Core B writes X = 2 simultaneously; Core C sees 1 then 2 while Core D sees 2 then 1, leaving memory permanently split-brained!
Crucial Scenarios Shared lookup tables, reading sensor feeds, banking balance checks, producer-consumer queues where one core updates a flag and another polls it. Multi-threaded counters, database transactions, ticket booking systems, lock acquisition where multiple cores concurrently modify shared variables.
Mechanisms to Maintain Cache invalidation broadcasts (forcing a cache miss so the reader fetches fresh data), snooping bus read-miss interventions (dirty owner supplies fresh block). Write-serialization via a shared bus or central directory, Exclusive ownership acquisition before writing (MESI Modified/Exclusive states), atomic locks/barriers, Write-Through or Write-Back coherence protocols.

2.3 Cache Memory Organizations & Mapping Techniques (WITH ALL PYQ NUMERICALS!)

When the CPU wants data from a memory address, it checks the cache first. If the data is there, it's a Cache Hit (fast!). If not, it's a Cache Miss (slow—the CPU must stall while the block is fetched from Main Memory and copied into the cache).

Hit Ratio (H) = Hits / (Hits + Misses)   |   Miss Rate = 1 − H AMAT = Hit Time + ( Miss Rate × Miss Penalty ) AMAT = Average Memory Access Time. (Note: In some simpler textbook questions where memory access time is given directly as the miss cost, AMAT = H × Tcache + (1−H) × (Tcache + Tmemory) = Tcache + (1−H) × Tmemory, OR for simultaneous lookup: H × Tcache + (1−H) × Tmemory. Always state the formula you use clearly!)

The Three Cache Mapping Techniques

Main memory is sliced into equal-sized chunks called Blocks. Cache memory is sliced into slots of the exact same size called Lines. Because RAM has millions of blocks and Cache has only hundreds of lines, we need a rule for where a RAM block is allowed to sit inside the cache. There are three classic rules:

  1. Direct Mapping (1-Way): Every RAM block has exactly ONE assigned seat in the cache: Cache Line = (Block Address) mod (Number of Cache Lines).
    • Address split: [ TAG | LINE INDEX | BLOCK OFFSET ].
    • Pros: Super cheap, super fast lookup, zero replacement algorithm needed (the new block simply kicks out whoever is sitting in that seat).
    • Cons: High Conflict Misses (thrashing)—if two hot variables map to the same seat, they keep kicking each other out even when the rest of the cache is empty!
  2. Fully Associative Mapping: Free seating! Any RAM block can sit in any cache line.
    • Address split: [ TAG | BLOCK OFFSET ] (no index bits!).
    • Pros: Zero conflict misses; best possible hit rate.
    • Cons: Expensive! Hardware must compare the Tag against every single cache line simultaneously using parallel comparators, which burns power and slows hit time. Needs a replacement policy (LRU/FIFO/Random).
  3. K-Way Set-Associative Mapping (The Sweet Spot!): The cache is divided into Sets, and each Set contains K lines (e.g., 2-way, 4-way, 8-way). A RAM block maps to ONE specific Set (Set Index = Block Address mod Number of Sets), and can sit in any of the K seats inside that Set!
    • Address split: [ TAG | SET INDEX | BLOCK OFFSET ].
    • Number of Sets: (Total Cache Lines) / K.
    • Pros: Combines the speed of Direct Mapping with the low conflict misses of Fully Associative! Modern L1/L2/L3 caches are almost always 4-way, 8-way, or 16-way set-associative.

2.4 The 3 C's of Cache Misses & Advanced Cache Optimizations

Every cache miss in the universe falls into one of three causes—memorize The 3 C's:

  • Compulsory Misses (Cold Start Misses): The very first time a block is ever requested, it obviously isn't in the cache yet. Even an infinite cache suffers compulsory misses! Fix: Larger block sizes or prefetching.
  • Capacity Misses: The cache simply isn't big enough to hold all the blocks your program is actively using, so blocks get evicted and later requested again. Fix: Increase total cache size.
  • Conflict Misses (Collision Misses): Even though the cache has plenty of room, multiple blocks map to the exact same line or set and keep kicking each other out (happens in Direct-Mapped and Set-Associative caches, never in Fully Associative). Fix: Increase associativity (e.g., 2-way → 4-way) or add a Victim Cache.

The 2:1 Cache Rule of Thumb: A Direct-Mapped cache of size $N$ has roughly the same miss rate as a 2-way Set-Associative cache of size $N/2$!

PYQ Spotlight — Dec 2024 Q1(c)

Question: Design an optimization strategy to improve cache performance in a given system. Discuss its impact on coherence and locality.

Remember the AMAT equation: $\text{AMAT} = \text{Hit Time} + \text{Miss Rate} \times \text{Miss Penalty}$. Therefore, EVERY cache optimization attacks one of three levers:

  1. Reducing Miss Rate:
    • Larger Block Size: Exploits spatial locality to cut compulsory misses (careful: too large increases miss penalty and conflict misses, and causes false sharing in multiprocessor coherence!).
    • Higher Associativity & Larger Cache Size: Slashes conflict and capacity misses.
    • Victim Cache: A tiny, super-fast fully associative buffer (4–16 entries) that catches blocks just evicted from L1, saving conflict misses cheaply.
    • Hardware / Software Prefetching: Predicts future addresses (like array strides) and fetches them before the CPU asks.
    • Compiler Optimizations (Loop Interchange & Blocking/Tiling): Reorganizes matrix loops so data is accessed row-by-row (boosting spatial and temporal locality) without touching hardware!
  2. Reducing Miss Penalty:
    • Multilevel Caches (L1, L2, L3): Keep L1 tiny and fast; let huge L2/L3 catch L1 misses so you rarely touch slow DRAM.
    • Critical Word First & Early Restart: Send the exact word the CPU is waiting for first, let the CPU resume immediately, and fill the rest of the block in the background.
    • Non-Blocking (Lockup-Free) Caches: "Hit under miss"—allow the cache to keep serving other hits while waiting on a miss.
  3. Reducing Hit Time:
    • Small, Simple L1 Caches (split into L1-Instruction and L1-Data caches).
    • Pipelined Cache Access and Way Prediction (guessing which set-associative way holds the block).
    • Virtually Indexed, Physically Tagged (VIPT) Caches: Overlap cache lookup with TLB address translation.

Impact on Coherence & Locality: Bigger caches and larger blocks boost spatial/temporal locality, but in multi-core systems, larger blocks can worsen False Sharing (two cores editing two unrelated variables that happen to sit in the same 64-byte cache line, triggering needless coherence invalidations!), and multi-level caches require strict inclusion/coherence protocols across L1, L2, and shared L3.

2.5 Cache Write Policies, Cache Coherence & Synchronization

Write Policies: Write-Through vs. Write-Back

  • Write-Through (WT): Every time the CPU writes to cache, it immediately writes the same value to Main Memory too. Simple and keeps RAM always fresh, but creates heavy memory bus traffic. Two variants in multiprocessors: WT with Update (broadcasts new data to all other caches) and WT with Invalidation (broadcasts an invalidate signal so other caches drop stale copies).
  • Write-Back (WB): Writes happen only in the cache, and a Dirty (Modified) Bit is set to 1. Main Memory is updated only later when that cache line is evicted/flushed. Much faster and saves bus bandwidth, but Main Memory temporarily holds stale data—making coherence protocols mandatory!

The Cache Coherence Problem & Solutions

In a multi-core CPU, Core 0 and Core 1 each have their own private L1/L2 caches. Suppose both read X = 10. Then Core 0 writes X = 99 to its private cache. If Core 1 now reads X from its own cache, it still sees 10—program corruption! How do we fix this?

  • Software-Level Solution (Compiler-Based): The compiler analyzes the code, spots shared variables that might become inconsistent, and marks them as uncacheable (forcing direct RAM access). Simple hardware, but slow performance.
  • Hardware Solution 1 — Snoopy Protocols (Best for Bus-Based SMPs, ≤ 16 cores): All caches connect to a shared broadcast bus. Every cache controller constantly "snoops" (eavesdrops) on bus traffic.
    • Write-Invalidate Protocol (Most common, e.g., MESI): Multiple readers allowed, only ONE writer at a time. Before writing to a shared line, Core 0 broadcasts an Invalidate message on the bus; all other caches mark their copy Invalid. Core 0 now has exclusive ownership and can write freely locally!
    • Write-Update (Write-Broadcast) Protocol: Whenever Core 0 writes a word, it broadcasts the new word over the bus so all other caches holding that line update it immediately. Higher bus traffic, lower read-miss latency.
    • Key Cache Events: Read-Hit (local, no bus traffic); Read-Miss (bus-read; if a remote cache holds a dirty copy, it intervenes and supplies the fresh block); Write-Hit (if dirty/exclusive, write locally; if shared/valid, broadcast write-invalidate); Write-Miss (broadcast read-invalidate to grab exclusive ownership and invalidate others); Block Replacement (if dirty, write back to RAM; otherwise just overwrite).
  • Hardware Solution 2 — Directory-Based Protocols (Best for Large NUMA/DSM Systems, 64–1000+ cores): Broadcasting to 500 cores clogs a bus instantly. Instead, a Directory (stored in main memory / distributed memory controllers) keeps a neat checklist of which caches currently hold a copy of every memory block. When Core 0 wants to write, it asks the Directory; the Directory sends targeted point-to-point invalidation messages ONLY to the specific cores that hold a copy, waits for acknowledgments, and grants exclusive access. Drawbacks: Central directory controller can become a bottleneck (solved by distributing the directory across nodes) and adds indirection latency.

2.6 Virtual Memory, Page Replacement & Virtual Machines

PYQ Spotlight — Dec 2022 Q2(c) & Dec 2023 Q2(c)

Questions: (1) What is virtual memory, how does it differ from physical RAM, and how does it abstract and extend physical memory? (2) Calculate the maximum protection/control bits in a Page Table Entry (PTE).

Virtual Memory (VM) is one of the greatest magic tricks in computing. Suppose your laptop has only 8 GB of physical RAM, yet you simultaneously open Chrome (6 GB), VS Code (3 GB), and a video game (12 GB). Why doesn't your laptop explode? Because the Operating System and CPU team up to create an illusion: every program thinks it owns a massive, private, contiguous block of RAM starting at address 0!

In reality, Virtual Memory slices a program's Virtual Address Space (Logical Address) into fixed-size chunks called Pages (typically 4 KB), and slices physical RAM (Memory Space / Physical Address) into matching slots called Page Frames. Only the actively needed pages sit in fast RAM; the rest sleep peacefully on the hard drive/SSD (swap space).

  1. The CPU generates a Virtual Address = [ Virtual Page Number (VPN) | Page Offset ].
  2. The Memory Management Unit (MMU) looks up the VPN in the Page Table (accelerated by a super-fast hardware cache called the TLB — Translation Lookaside Buffer!).
  3. If the page's Valid/Present bit is 1, the MMU swaps the VPN for the Physical Frame Number (PFN), attaches the exact same Offset, and fetches the data from RAM.
  4. If the Valid bit is 0, a Page Fault triggers! The OS pauses the program, fetches the missing page from the Disk/SSD into a free RAM frame, updates the Page Table, and restarts the instruction.

Page Replacement Algorithms (When RAM Is Full!)

When a Page Fault occurs and every RAM frame is already full, the OS must evict an existing page to disk using a Page Replacement Algorithm:

  • FIFO (First-In, First-Out): Evicts the page that has been sitting in RAM the longest (like a queue). Dead simple to build, but ignores whether that old page is still heavily used (can even suffer from Belady's Anomaly—adding more RAM causes more faults!).
  • LRU (Least Recently Used): Evicts the page that hasn't been touched for the longest time (exploits temporal locality). Often implemented using aging counters (reset to 0 when referenced, incremented periodically; highest count gets evicted). Great performance, higher hardware cost.
  • Optimal (OPT / Belady's Algorithm): Evicts the page that will not be needed for the longest time in the future. Guarantees the absolute minimum page faults, but is impossible to implement in real life (the OS cannot see the future!). Used strictly as a theoretical benchmark to grade FIFO and LRU.

Virtual Machines (VMs)

Just as Virtual Memory gives each program the illusion of owning all RAM, a Virtual Machine (VM) gives an entire Operating System (Guest OS) the illusion of owning an entire physical computer! A thin software/hardware layer called the Virtual Machine Monitor (VMM) or Hypervisor sits underneath and multiplexes physical CPU, RAM, and I/O across multiple isolated VMs:

  • Type-1 (Bare-Metal) Hypervisor: Runs directly on physical hardware (e.g., VMware ESXi, Microsoft Hyper-V, Xen). Ultra-fast, powers cloud data centers like AWS and Google Cloud.
  • Type-2 (Hosted) Hypervisor: Runs as an app inside a Host OS (e.g., VirtualBox, VMware Workstation). Great for students testing Linux inside Windows.
  • Why VMs Matter: Server consolidation (run 20 servers on 1 physical box), strong security isolation (if one VM gets hacked, others survive), and legacy OS compatibility.

The Assembly Line of Silicon: Pipelining, Reservation Tables & Hazards

"One baker frosting one cake from start to finish is charming. Five bakers passing cakes down a pastel conveyor belt—one mixing, one baking, one frosting, one boxing, one tying the pink ribbon—is an empire."

3.1 Basics of Pipelining: The Factory Assembly Line Inside Your CPU

Suppose you want to make a CPU faster. You only have two choices: (1) build faster, pricier silicon circuits (which quickly hits physical heat limits), or (2) overlap multiple instructions so several are executing simultaneously. That second genius idea is called Pipelining.

Formally, Pipelining is the technique of decomposing a sequential process (like executing one instruction) into smaller sub-operations called Stages (or Segments), each handled by dedicated hardware that operates concurrently with all other stages, separated by Pipeline Registers (Latches) and synchronized by a global clock.

Analogy Corner — Mendl's Pastry Assembly Line

Baking one Courtesan au Chocolat takes 5 steps of 10 minutes each = 50 minutes total. Without pipelining, baking 4 pastries back-to-back takes $4 \times 50 = 200$ minutes. With a 5-stage pipeline (Station 1: Dough, Station 2: Bake, Station 3: Cream, Station 4: Glaze, Station 5: Box), Pastry #1 still takes 50 minutes—pipelining NEVER reduces the latency of a single instruction!—but once the line is full, a fresh finished pastry pops off the conveyor belt every 10 minutes! Pipelining massively increases Throughput (instructions completed per unit time), aiming for an ideal CPI = 1.

Historical Interlude — From Henry Ford to IBM Stretch

Henry Ford revolutionized car manufacturing in 1913 with the moving assembly line. Four decades later, computer pioneers brought the exact same trick into silicon: the IBM 7030 "Stretch" (1961) and CDC 6600 (1964) introduced instruction pipelining, and by the 1980s, the 5-stage RISC pipeline (MIPS / DLX) became the gold standard taught in every university on Earth.

3.2 Linear vs. Nonlinear Pipelines (and Synchronous vs. Asynchronous)

PYQ Spotlight — Dec 2023 Q3(a)

Question: What is a linear pipeline, and how does it differ from non-linear pipelines in terms of task execution and sequencing? Give an overview of key characteristics of linear pipelines.

Not every assembly line is a straight conveyor belt! Pipelines come in two structural families:

  • Linear Pipeline Processor: A straight cascade of processing stages ($S_1 \to S_2 \to S_3 \to \dots \to S_k$) performing a fixed function over a stream of data flowing strictly from one end to the other.
    • Key Characteristics: Every stage performs one dedicated sub-task; output of stage $i$ feeds strictly into stage $i+1$; no feedback loops and no feedforward bypasses; simple control logic; predictable high throughput. Example: the classic 5-stage RISC instruction pipeline.
    • Synchronous vs. Asynchronous Linear Pipelines: In a Synchronous pipeline, one global clock ticks and all latches transfer data simultaneously (stage clock period = slowest stage + latch delay). In an Asynchronous pipeline, there is no global clock—adjacent stages use Ready/Acknowledge handshaking signals to pass data whenever they finish.
  • Nonlinear (Dynamic) Pipeline Processor: A flexible, multifunctional pipeline that allows feedback loops (a task revisits an earlier stage), feedforward connections (skipping stages), and multiple parallel paths.
    • Key Characteristics: Can perform multiple different functions (multifunctional); tasks do not follow a fixed linear order; requires complex scheduling via Reservation Tables to prevent two tasks from colliding in the same stage at the same time! Examples: Floating-point division units, vector processors, DSPs, AI accelerators, and modern superscalar pipelines.

3.3 The Classic 5-Stage RISC Instruction Pipeline & Arithmetic Pipelines

PYQ Spotlight — Dec 2024 Q2(a)

Question: Describe the five-stage RISC pipeline and highlight common performance issues in pipelining.

Every RISC instruction (like MIPS or RISC-V) marches smoothly through 5 clean, equal-length stages, with pipeline registers (IF/ID, ID/EX, EX/MEM, MEM/WB) holding intermediate values between clock ticks:

Exhibit 3.1 — The 5-Stage RISC Instruction Pipeline (Dark bars = Pipeline Registers / Latches)
  1. IF (Instruction Fetch): Read the next instruction from Instruction Memory using the Program Counter (PC), and increment PC ← PC + 4.
  2. ID (Instruction Decode & Register Fetch): Decode the opcode into control signals and read the source registers (e.g., R2, R3) from the Register File.
  3. EX (Execute / Effective Address): The ALU performs arithmetic/logic (e.g., R2 + R3), computes a memory address for Load/Store, or evaluates a branch condition/target.
  4. MEM (Memory Access): Only LOAD and STORE instructions do real work here—reading from or writing to Data Memory. Pure ALU instructions just pass through.
  5. WB (Write Back): Write the final result (from ALU or Memory) back into the destination register in the Register File.

Arithmetic Pipeline Design (Floating-Point Adder Example)

Besides instruction pipelines, CPUs use Arithmetic Pipelines to chew through heavy math like floating-point addition ($X = A \times 2^a$, $Y = B \times 2^b$) or multiplication. A classic Floating-Point Addition Pipeline splits the math into 5 clean stages: (1) Exponent Comparison ($d = |a - b|$) → (2) Mantissa Alignment (shift the smaller number's mantissa right by $d$ bits) → (3) Mantissa Addition/Subtraction → (4) Normalization (shift result and adjust exponent so leading digit is 1) → (5) Rounding.

3.6 Pipeline Hazards: The Three Villains That Cause Stalls

PYQ Spotlight — Dec 2022 Q3(c)(i), Dec 2023 Q3(b,c), Dec 2024 Q3(c)

Asked EVERY year! List pipelining hazards with examples, explain how branch hazards hurt efficiency, and propose mitigation strategies.

In a dream world, a pipeline finishes 1 instruction every single clock tick ($\text{CPI} = 1$). In reality, obstacles called Pipeline Hazards force the pipeline to pause—inserting empty idle cycles called Stalls (or Bubbles), so $\text{CPI}_{\text{pipelined}} = 1 + \text{Stall Cycles per Instruction}$. There are three classes of hazards:

1. Structural (Resource) Hazards — "Not Enough Hardware!"

Cause: Two instructions in different stages try to use the exact same piece of hardware in the same clock cycle. Classic Example: If a CPU has only ONE unified memory, Instruction 1 (in stage 4, MEM, loading data) and Instruction 4 (in stage 1, IF, fetching an instruction) collide in Cycle 4!

Solutions: (a) Split Memory (Harvard Architecture / Renaming): Separate L1 Instruction Cache (Code Memory) and L1 Data Cache (Data Memory); (b) Duplicate Functional Units: Add multiple ALUs or multi-ported register files; (c) Stall the later instruction until the resource is free.

2. Data Hazards — "I Need Your Answer Before You've Finished!"

Cause: Instruction 2 depends on the result of Instruction 1, which is still halfway down the pipeline and hasn't written its answer back to the register file yet!

EXAMPLE OF RAW DATA HAZARD: I1: ADD R1, R2, R3 ; computes R1 = R2 + R3 (writes R1 in Stage 5: WB) I2: SUB R4, R1, R5 ; needs R1 in Stage 2: ID! If it doesn't wait, it reads OLD R1!

The three types of Data Hazards (also deeply tested in Unit 4!) are:

  • RAW (Read After Write — True / Flow Dependency): $J$ tries to read a register before $I$ writes it. The ONLY true data dependency—cannot be eliminated by renaming!
  • WAR (Write After Read — Anti-Dependency): $J$ tries to write a register before $I$ finishes reading its old value (occurs in out-of-order execution).
  • WAW (Write After Write — Output Dependency): $J$ writes to the same destination register before $I$ finishes writing to it (occurs in out-of-order execution).

Solutions to Data Hazards: (a) Operand Forwarding (Bypassing): Wire a shortcut directly from the output of the ALU (EX/MEM register) straight back into the ALU input of the next instruction—eliminating the stall without waiting for WB! (b) Pipeline Stalling (Interlocks/Bubbles): Necessary for a Load-Use Hazard (when LOAD data isn't ready until after MEM); (c) Compiler Instruction Scheduling: Reorder independent instructions to fill the gap; (d) Register Renaming (eliminates WAR & WAW).

3. Control (Branch) Hazards — "Which Fork in the Road?"

Cause: Conditional branches (BEQ, BNE, JMP) change the Program Counter (PC). When the CPU fetches a branch instruction in Stage 1 (IF), it does NOT yet know whether the branch will be taken or where it jumps until Stage 2 (ID) or Stage 3 (EX)! Meanwhile, it already blindly fetched the next 1–2 instructions into the pipeline. If the branch IS taken, those blindly fetched instructions are WRONG and must be flushed (thrown away), wasting cycles—known as the Branch Penalty! Because ~20% of all instructions are branches, flushing a 15-stage pipeline ruins throughput.

Mitigation Strategies for Branch Hazards:

  1. Freeze / Flush (Stall): Simply stop fetching until the branch resolves. Simple, huge performance penalty.
  2. Early Branch Resolution: Move the branch comparator and target-address adder earlier from EX into ID to shrink penalty from 2 cycles to 1 cycle.
  3. Branch Delay Slots: The compiler places a useful, always-needed instruction right after the branch so that cycle isn't wasted.
  4. Loop Unrolling: Duplicate loop body 4× so you execute 4× fewer branch instructions!
  5. Static & Dynamic Branch Prediction (BHT + BTB): Guess the branch outcome right in Stage 1 (IF) using history tables (achieving 90–98% accuracy in modern CPUs—which we unpack in full glory in Unit 4!).

"A clever concierge does not wait for Guest #1's luggage to reach the fourth floor before handing Guest #2 their room key—provided, of course, they do not accidentally swap the rooms."

4.1 What is Instruction-Level Parallelism (ILP)? (And ILP vs. DLP)

PYQ Spotlight — Dec 2022 Q4(b), Dec 2023 Q4(b), Dec 2024 Q3(a)

Questions: (1) What is ILP, why is it important, and what are its fundamental principles and challenges? (2) Compare and contrast Instruction-Level Parallelism (ILP) and Data-Level Parallelism (DLP).

In Unit 3, pipelining allowed us to overlap instructions so we could complete at best 1 instruction per clock cycle ($\text{CPI} = 1$). But what if we want to shatter that barrier and finish 2, 4, or even 8 instructions every single clock cycle ($\text{CPI} < 1$, or $\text{IPC} > 1$)?

To do that, we exploit Instruction-Level Parallelism (ILP): the potential overlap and simultaneous execution of multiple independent instructions within a single program thread! Look at these two lines of code:

I1: R1 = R2 + R3 ; independent! I2: R4 = R5 * R6 ; uses completely different registers — can run AT THE EXACT SAME TIME as I1!

The Fundamental Challenge of ILP: Inside a single Basic Block (a straight-line sequence of instructions with no branches in or out), there are typically only 4 to 7 instructions, and many of them depend on each other! To find enough independent work to keep 4 or 8 execution units busy, compilers and hardware must look across branches (via branch prediction and loop unrolling) and untangle Data Dependencies.

4.2 Data Dependencies & Hazards Revisited (RAW, WAR, WAW)

PYQ Spotlight — Dec 2023 Q4(c) & Dec 2024 Q3(a)

Question: Explain RAW, WAR, and WAW data hazards, their causes, and their significance in ILP.

Remember the crucial distinction: a Dependency is a property of the program; a Hazard is a property of the pipeline (a dependency turns into a hazard if the hardware overlaps instructions closely enough to get the wrong answer). Suppose Instruction I comes before Instruction J:

  • 1. RAW (Read After Write) — True / Flow Dependency: J tries to read a register before I writes it.
    Example: I: R2 ← R1 + R3 followed by J: R4 ← R2 + R5.
    Cause & Fix: Real data flows from I to J. You cannot eliminate a RAW dependency by renaming—you can only speed it up with Operand Forwarding or wait (stall).
  • 2. WAR (Write After Read) — Anti-Dependency (Name Dependency): J tries to overwrite a register before I has finished reading its old value!
    Example: I: R2 ← R1 + R3 followed by J: R3 ← R4 + R5.
    Cause & Fix: Only happens in out-of-order execution! Notice J does NOT actually need I's data—they just accidentally reused the same register name R3! Fix: Register Renaming (give J a fresh temporary register T1 instead of R3!).
  • 3. WAW (Write After Write) — Output Dependency (Name Dependency): J finishes writing to a destination register before earlier instruction I finishes writing to that same register—leaving the stale value of I inside the register at the end!
    Example: I: R2 ← R1 / R3 (slow divide!) followed by J: R2 ← R4 + R5 (fast add!).
    Cause & Fix: Happens in out-of-order / variable-latency pipelines. Again, it's a false (name) dependency—completely eliminated by Register Renaming!

4.3 Basic Compiler Techniques for Exploiting ILP

Before hardware even touches the code, a smart Compiler can statically rearrange instructions to eliminate stalls and expose ILP:

  • Compiler Instruction Scheduling: Moves independent instructions into the "shadow" of slow instructions (like Loads or Floating-Point Multiplies) so the CPU does useful work instead of stalling.
  • Loop Unrolling: Suppose a loop runs 1,000 times adding a constant to an array. Every single iteration has loop-overhead instructions (increment counter i++ and conditional branch BNE). By unrolling the loop 4× (putting 4 iterations' worth of body code side-by-side in one iteration and incrementing i += 4), the compiler: (1) cuts branch overhead by 75%, (2) creates a huge basic block with plenty of independent instructions to schedule in parallel, and (3) uses different registers for each unrolled copy (static register renaming) to eliminate WAR/WAW! Trade-off: Larger code size and higher register pressure.
  • Software Pipelining: A symbolic compiler trick that overlaps instructions from different iterations of a loop—like running iteration $i$'s STORE, iteration $i+1$'s ADD, and iteration $i+2$'s LOAD simultaneously inside one loop body!

4.4 Advanced Branch Prediction (Direction, Correlating & Hierarchical Predictors)

PYQ Spotlight — Dec 2022 Q4(a), Dec 2023 Q4(a), Dec 2024 Q5(a)

EXACT REPEAT in 2022 & 2023! Write short notes on: (i) Branch Prediction, (ii) Direction Predictor, (iii) Hierarchical Predictors.

(i) Branch Prediction (Why Guessing Saves Modern CPUs)

Roughly 20% of all instructions are conditional branches. In a deep 15-stage, 4-wide superscalar CPU, a single branch misprediction flushes up to 60 instructions down the drain! Branch Prediction resolves control hazards by guessing the branch outcome right during the Fetch (IF) stage and speculatively executing down the predicted path. If the guess is right: zero penalty! If wrong: flush the wrong-path instructions and fetch the right path.

  • Static Branch Prediction: Fixed at compile time—never changes at runtime. Simple rules: Always Not-Taken, Always Taken, or BTFNT (Backward Taken, Forward Not-Taken)—because loops jump backward and usually repeat!
  • Dynamic Branch Prediction: Implemented in hardware; adapts continuously as program behavior changes at runtime using branch history.

(ii) Direction Predictors (1-Bit, 2-Bit & Correlating Predictors)

A Direction Predictor answers one binary question: Will this branch be TAKEN (T) or NOT-TAKEN (N)?

  • 1-Bit Branch Prediction Buffer (BHT): A small table indexed by the lower bits of the branch PC. Each entry stores 1 bit: whatever the branch did last time.
    The Flaw: In a nested loop like for(i=0; i<5; i++) (outcomes: T, T, T, T, N), a 1-bit predictor mispredicts TWICE per loop—once when exiting the loop (N flips the bit to 0), and AGAIN on the first iteration when re-entering the loop!
  • 2-Bit Saturating Counter (The Classic Direction Predictor!): Fixes the loop flaw by requiring TWO consecutive mistakes before flipping the prediction! It has 4 states: 11 Strongly Taken (ST), 10 Weakly Taken (WT), 01 Weakly Not-Taken (WN), and 00 Strongly Not-Taken (SN). When exiting a loop once, ST (11) merely drops to WT (10)—which STILL predicts Taken on the next entry! Only 1 misprediction per loop!
Exhibit 4.1 — The 2-Bit Saturating Counter Direction Predictor (Must Be Wrong Twice to Flip!)
  • Correlating (2-Level / Global) Predictors: Often, one branch's outcome depends on earlier branches! Example: if (x==2) x=0; if (y==2) y=0; if (x!=y) ...—if branches 1 & 2 are both taken, branch 3 is guaranteed NOT-taken! A correlating predictor shifts the outcomes of the last $m$ branches into a Global History Register (GHR) and uses it (combined with PC bits, as in gshare) to index a Pattern History Table (PHT) of 2-bit counters.

(iii) Hierarchical (Hybrid / Tournament) Predictors & Target Predictors

Why pick only ONE predictor when some branches prefer local history (like loops) and others prefer global history (like correlated if statements)? Hierarchical (Hybrid / Tournament) Predictors combine a Local Predictor and a Global Correlating Predictor in a multi-level hierarchy, with a 2-bit Meta-Predictor (Selector) that tracks which predictor has been more accurate for each branch and dynamically crowns the winner! (Used in DEC Alpha 21264, AMD, and modern Intel CPUs, achieving 95–99% accuracy!)

Predicting Target Addresses Early: Knowing a branch is "Taken" isn't enough—you also need the destination address in Stage 1! (1) Branch Target Buffer (BTB): A tiny cache storing [Branch PC → Predicted Target Address + Prediction Bits]; if it hits in IF, zero branch delay! (2) Return Address Stack (RAS): 85% of indirect jumps are function returns (RET). A small hardware stack pushes the return address on CALL and pops it on RET for near-100% accuracy! (3) Predicated Execution (e.g., Intel Itanium): Eliminates short branches altogether by executing both paths conditionally and discarding the false one—converting a control hazard into a harmless data hazard!

4.5 Dynamic Scheduling: Scoreboarding, Tomasulo's Algorithm & Speculation

In a simple in-order pipeline, if Instruction 1 stalls on a cache miss, Instruction 2—even if it is 100% independent—gets stuck behind it like a car trapped in a one-lane tunnel! Dynamic Scheduling (Out-of-Order Execution) lets hardware rearrange instructions on the fly so independent instructions zoom right past stalled ones.

  1. Scoreboarding (CDC 6600, 1964 — Seymour Cray): A central hardware "Scoreboard" tracks all functional units, register statuses, and dependencies across 4 stages: Issue → Read Operands → Execution → Write Result. Instructions execute out-of-order as soon as their operands are ready, HOWEVER, Scoreboarding does NOT have register renaming—so it must still stall on WAW (at Issue) and WAR (at Write Result).
  2. Tomasulo's Algorithm (IBM 360/91, 1967 — Robert Tomasulo): The crown jewel of modern CPU design! Tomasulo solved Scoreboarding's limitations using three brilliant inventions:
    • Reservation Stations (RS): Waiting buffers right in front of each functional unit (Adders, Multipliers) that hold instructions and their operand values (or tags saying which RS will produce a missing operand).
    • Hardware Register Renaming: Renames architectural registers to Reservation Station tags—completely eliminating ALL WAR and WAW hazards!
    • Common Data Bus (CDB): When any unit finishes computing a result, it broadcasts (Tag, Value) on the CDB—simultaneously feeding every waiting Reservation Station and the Register File in one shot!
  3. Hardware-Based Speculation & Reorder Buffer (ROB): Tomasulo + Branch Prediction = Speculative Execution! To ensure a mispredicted branch or exception never corrupts real registers, results are held inside a circular FIFO queue called the Reorder Buffer (ROB). Instructions execute out-of-order, but Commit (retire) strictly IN-ORDER! If a branch was mispredicted, simply flush the ROB entries after the branch—clean, precise recovery!

4.6 Multiple-Issue Processors & Duplicating Register Value Policies

To achieve $\text{CPI} < 1$ (finishing multiple instructions per cycle), CPUs use Multiple-Issue Architectures:

  • Superscalar Processors: Hardware fetches, decodes, and issues a variable number (2 to 8) of instructions every clock cycle. Can be Static-Issue (compiler schedules, hardware checks) or Dynamic-Issue (out-of-order Tomasulo + ROB + speculation—used in almost all modern Intel, AMD, and Apple CPUs!).
  • VLIW (Very Long Instruction Word) & EPIC: Instead of expensive runtime scheduling hardware, the compiler packs 3 to 8 independent operations into one giant "bundle" instruction executed in lockstep. Simpler hardware, lower power, great for DSPs, but suffers from code bloat (NOPs) and poor binary compatibility across generations.
PYQ Spotlight — Dec 2022 Q4(c) (10 Marks)

Question: Explain the duplicating register value policies in detail.

In advanced high-ILP, multiple-issue, and speculative processors, having just ONE single copy of every architectural register creates massive bottlenecks: (1) false dependencies (WAR/WAW) stall execution, (2) speculative mispredictions need to roll back register values cleanly, (3) function calls waste time saving/restoring registers to RAM, and (4) wide superscalar CPUs need too many read/write ports on one centralized Register File (which explodes wire delay and area!).

To solve these problems, architects use Duplicating Register Value Policies—maintaining multiple physical copies or versions of register values:

  1. Register Renaming (Physical Register File / Reorder Buffer Duplication): The CPU maintains a large pool of hidden Physical Registers (e.g., 180 physical registers backing just 16 architectural x86 registers). Whenever an instruction writes to R1, the Rename Table maps R1 to a brand-new physical register P47 while keeping the old value alive in P12 for earlier instructions. Multiple versions of R1 coexist simultaneously, eliminating WAR/WAW hazards!
  2. Shadow Register Files (Fast Interrupt & Context Switch Duplication): Hardware keeps one or more complete duplicate "shadow" copies of the register set. When an interrupt or fast context switch arrives, the CPU simply flips a pointer to the shadow bank in 1 clock cycle instead of painfully saving 32 registers to RAM!
  3. Register Windows (e.g., Sun SPARC): Duplicates register banks into overlapping "windows" (In, Local, Out registers) so that calling a function simply slides the active window pointer—passing arguments instantly without spilling to memory.
  4. Register Checkpointing (Speculative State Duplication): Right before executing a risky conditional branch, the CPU takes a snapshot (duplicate copy) of the Register Alias Table (RAT) / register state. If the branch mispredicts, the CPU restores the checkpoint in 1 cycle!
  5. Replicated (Clustered) Register Files: In wide superscalar / VLIW processors (e.g., Alpha 21264), instead of one huge 16-port register file, hardware maintains two synchronized duplicate copies of the entire register file—one for Cluster A's ALUs and one for Cluster B's ALUs. Reads are ultra-fast locally, and writes broadcast across clusters (with a 1-cycle sync delay).

5.1 Taxonomy of Parallel & Multiprocessor Architectures

PYQ Spotlight — Dec 2022 Q5(a) & Dec 2024 Q5(c)

Question: Classify multi-processing computer architectures in the context of parallel architectures.

When single-core clock speeds hit the Power Wall around 2004, the entire computer industry pivoted from making one core faster to putting many cores and processors together. Multiprocessor architectures are classified along three clean axes:

  1. Instruction & Data Streams (Flynn's Taxonomy): SISD, SIMD, MISD, and MIMD (the dominant class for general-purpose multiprocessors!).
  2. Memory Organization (Physical vs. Logical View):
    • Shared-Memory Multiprocessors: All processors share a single global address space—either physically centralized (UMA / SMP) or physically distributed (NUMA / DSM).
    • Distributed-Memory Multicomputers (Message Passing): Each processor has its own private local memory; processors communicate strictly by sending explicit messages over a network (clusters, supercomputers).
    • Hybrid Distributed-Shared Memory: Modern supercomputers! Clusters of multi-core shared-memory nodes wired together with high-speed message-passing interconnects (e.g., MPI between nodes + OpenMP inside each node).
  3. Coupling & Granularity: Tightly Coupled (shared memory, fine/medium-grained) vs. Loosely Coupled (distributed memory, coarse-grained).

5.3 Message Passing vs. Shared Memory (& Database Management Case Study)

PYQ Spotlight — Dec 2023 Q5(a) & Dec 2024 Q2(c)

Questions: (1) Compare advantages and disadvantages of Message Passing vs. Shared Memory. (2) Evaluate trade-offs between Message Passing and Shared Memory for a real-world application like Database Management (DBMS).

Analogy Corner — The Shared Whiteboard vs. Sealed Letters

Shared Memory is like four coworkers standing around ONE big whiteboard: anyone can read or erase any number instantly, which is super convenient—but if two people grab the marker at once, chaos erupts unless they use a talking stick (locks/mutexes)! Message Passing is like four coworkers in separate locked offices who communicate strictly by sliding envelopes (MPI_Send / MPI_Recv) under each other's doors: zero accidental overwriting, scales to 10,000 offices across the world, but takes effort to pack and mail every letter!

Real-World Case Study — Database Management System (DBMS) (Dec 2024 Q2c):

  • Shared-Memory DBMS (e.g., single-server PostgreSQL / MySQL / Oracle SMP): Shines for OLTP (Online Transaction Processing) with complex SQL joins and ACID transactions touching overlapping tables. Shared buffer pools and in-memory lock tables give sub-millisecond latency. Weakness: Hits a vertical scaling wall (you can only buy so much RAM/CPU in one box) and single point of failure!
  • Message-Passing / Shared-Nothing DBMS (e.g., Google Spanner, Cassandra, CockroachDB, Sharded MongoDB): Shines for petabyte-scale Big Data & global web apps! Data is partitioned ("sharded") across thousands of cheap machines. Scales horizontally forever and survives server crashes gracefully. Weakness: Cross-shard joins and distributed transactions (Two-Phase Commit / Paxos) incur heavy network message overhead!

5.4 Tightly Coupled vs. Loosely Coupled Systems: Issues & Solutions

PYQ Spotlight — Dec 2022 Q5(c) (10 Marks)

Question: List various issues and their solutions in loosely coupled and tightly coupled systems.

Tightly Coupled Systems are shared-memory multiprocessors (SMP/NUMA) running under a single OS where processors share RAM and communicate at nanosecond speeds. Loosely Coupled Systems are distributed multicomputers/clusters where independent machines have private RAM, their own OS, and talk over a network (LAN/WAN). Each faces distinct engineering headaches:

System Type Major Issues / Challenges Engineering Solutions
Tightly Coupled Systems
(Shared Memory)		 1. Cache Coherence & False Sharing: Private caches hold stale copies; unrelated variables on the same cache line ping-pong. Hardware Snoopy (MESI) or Directory protocols; compiler data padding/alignment to prevent false sharing.
2. Memory Bus / Interconnect Contention: Too many cores fighting over one bus stalls the system. Large private L1/L2 caches to filter bus traffic; replace shared bus with Crossbar switches, Mesh networks, or NUMA.
3. Synchronization Overhead & Deadlocks: Spinlocks waste CPU cycles; improper lock ordering freezes threads. Hardware atomic instructions (Compare-And-Swap, LL/SC), lock-free data structures, Transactional Memory.
4. Single Point of Failure & Limited Scalability: One OS crash kills all cores. Hardware ECC memory, redundant power/paths, transitioning to clustered NUMA/Hybrid architectures.
Loosely Coupled Systems
(Distributed / Clusters)		 1. High Network Latency & Comm. Overhead: Sending messages across cables is 1000× slower than RAM. RDMA (Remote Direct Memory Access), InfiniBand, overlapping computation with non-blocking MPI_Isend, coarse-grained partitioning.
2. Load Imbalance: Some nodes sit idle while one overloaded node lags behind ("stragglers"). Dynamic load balancing, work-stealing schedulers, adaptive task migration.
3. Partial Failures & Fault Tolerance: In a 1,000-node cluster, a server dies every day! Data replication (RAID/HDFS), periodic Checkpointing & Rollback, heartbeat monitoring & automatic failover.
4. Distributed Consensus & Clock Skew: No global clock; nodes disagree on event order. Logical clocks (Lamport timestamps), NTP/PTP clock sync, consensus protocols (Paxos, Raft).

5.5 Thread-Level, SIMD, Vector, Associative, Neural & Systolic Architectures

A. Hardware Multithreading (Fine-Grained, Coarse-Grained & SMT)

When a single thread stalls for 200 cycles waiting on a DRAM cache miss, the CPU's expensive ALUs sit completely empty! Hardware Multithreading keeps multiple threads' register states on-chip so the CPU can instantly switch to another ready thread:

  • Fine-Grained Multithreading: Switches between threads on every single clock cycle (round-robin). Hides both short and long stalls effortlessly, but slows down any single thread's solo speed (e.g., Sun Niagara T1).
  • Coarse-Grained Multithreading: Runs one thread at full speed and switches ONLY when a costly long-latency stall occurs (like an L2/L3 cache miss). Great single-thread speed, but doesn't hide short 1–2 cycle stalls.
  • Simultaneous Multithreading (SMT / Intel Hyper-Threading): The cleverest of all! On a wide superscalar CPU, instructions from multiple different threads are issued in the EXACT SAME clock cycle—converting Thread-Level Parallelism (TLP) into Instruction-Level Parallelism (ILP) to fill every empty execution slot!

B. SIMD & Vector Architectures (WITH DEC 2023 PYQ!)

PYQ Spotlight — Dec 2023 Q5(c) (10 Marks)

Question: What is a vector architecture, and how does it differ from scalar architectures and traditional general-purpose processors? Give an overview of the key characteristics of vector processors.

Historical Interlude — Seymour Cray & The Legendary Cray-1 (1976)

In 1976, supercomputer genius Seymour Cray unveiled the Cray-1—shaped like a circular C-shaped loveseat (so wires across the back were as short as possible!) with a leather-cushioned bench around the base covering the power supplies. It was the world's most iconic Vector Supercomputer, chewing through weather forecasting and aerospace physics at 160 MFLOPS when ordinary computers crawled!

A traditional Scalar Processor operates on ONE single number at a time: to add two arrays of 64 numbers, it must fetch, decode, and execute a LOAD, ADD, STORE, and BRANCH loop 64 separate times (~256+ instructions!).

A Vector Processor (a pipelined form of SIMD) grabs an entire 1D array of 64 numbers into huge Vector Registers (e.g., V1, V2) and executes ONE single instruction—ADDV V3, V1, V2—streaming all 64 pairs through deeply pipelined arithmetic units!

  • Key Characteristics of Vector Architectures:
    1. Huge Vector Register Files: E.g., 8 to 32 vector registers, each holding 64 elements of 64 bits!
    2. Zero Intra-Vector Data Hazards: The hardware knows element 0 is completely independent of element 1, 2, ..., 63—so it needs ZERO complex dependency checking and ZERO branch prediction!
    3. Multiple Vector Lanes: Add 4 or 8 parallel arithmetic lanes and finish 4–8 vector elements per clock cycle!
    4. Vector Chaining: Just like operand forwarding for vectors—as soon as element 0 exits the Vector Multiplier, it immediately streams into the Vector Adder without waiting for all 64 multiplies to finish!
    5. Strip Mining: Automatically breaks arrays longer than the hardware vector length (e.g., 500 elements on a 64-element machine) into neat chunks.
    6. Vector Mask Registers & Scatter-Gather: Handles if conditions inside loops (masking off elements) and sparse/non-contiguous arrays (Gather from memory, Scatter back to memory).

C. Associative, Neural & Systolic Architectures

  • Associative Architecture (Content-Addressable Memory — CAM): Normal RAM works like postal mailboxes: you give it an address (Box #42) and it returns the contents. An Associative Memory (CAM) works in reverse: you shout out the contents (e.g., "Find IP 192.168.1.5") and EVERY memory cell compares its value simultaneously in parallel in 1 clock cycle! Used inside TLBs, Fully Associative Caches, and high-speed internet routers.
  • Neural Architectures (Neuromorphic & AI Accelerators): Inspired by the human brain's massively parallel network of neurons and synapses. Unlike von Neumann machines (bottlenecked by shuttling data back and forth from RAM), Neural Architectures (like Google's TPU, IBM TrueNorth, Intel Loihi, and NVIDIA Tensor Cores) place tiny multiply-accumulate (MAC) units right next to local weight memory to perform trillions of matrix operations per second at tiny power budgets!
  • Data-Parallel Pipelined & Systolic Architectures: Invented by H.T. Kung & Charles Leiserson (1978), the word "Systolic" comes from systole—the rhythmic pumping of the human heart! In a Systolic Array, a grid of simple, identical Processing Elements (PEs) is wired only to immediate neighbors. Data is pumped rhythmically from memory into the edge of the grid, flows step-by-step from PE to PE like blood cells through capillaries (being multiplied and accumulated at every heartbeat!), and exits the far side. Why is it genius? Each data item is fetched from slow RAM once and reused dozens of times inside the grid—slashing memory bandwidth! Today, Google's TPU Matrix Multiply Unit (MXU) is literally a giant 128×128 Systolic Array!
